# Criterion benchmark methodology

## Purpose

These benchmarks provide reproducible performance measurements for the public FerrousLearn APIs:

- `KMeans::fit` and `KMeans::predict`
- `PrincipalComponentAnalysis::transform`
- `LinearRegression::fit` / `predict`
- `LogisticRegression::fit` / `predict`

They are intended as local regression checks, not as a claim that one machine or build is universally faster than another.

## Reproducibility notes

- Inputs are generated deterministically from fixed formulas; no random crate is used in fixtures.
- KMeans uses a fixed seed for model initialisation.
- Benchmarks call the public API only.
- Fit benchmarks keep construction/setup outside the timed section with `iter_batched`.
- Prediction benchmarks prefit models once before timing.
- PCA fixtures are validated once before timing and use bounded QR iterations so failures surface immediately instead of being masked.
- All benchmark closures unwrap results intentionally; any convergence or validation error fails the run rather than producing misleading timing data.
- Criterion output is generated locally when the benchmarks are run and is not committed to the repository.

## Fixture design

### KMeans

- Two sample sizes: 100 and 1,000 rows.
- Four features per row.
- Four well-separated synthetic clusters.
- Small deterministic perturbations prevent identical rows while keeping convergence stable.
- Benchmarks cover both fit and predict.

### PCA

- Two matrix sizes: 64×4 and 128×4, each projected to three components.
- Nonconstant deterministic values derived from trig/polynomial combinations.
- A preflight transform validates the fixture and ensures the bounded QR settings converge before timing.

### Regression

- Two sample sizes: 128 and 1,024 rows with four features.
- Prediction fixtures contain 64 and 512 rows respectively, and benchmark IDs/throughput report those actual row counts.
- Linear targets follow a deterministic affine relationship.
- Logistic targets are generated by a deterministic threshold on the same feature space.
- Fit and predict are benchmarked separately so model-training cost is not conflated with prediction cost.

## Limitations

- Criterion is statistical: reported timings vary across runs, thermal conditions, and background system load.
- These fixtures are intentionally small enough to run on a low-power ARM host; they are not representative of all production workloads.
- The benchmarks measure the current implementation only; they do not compare against external libraries.
- Results depend on the Rust compiler, Criterion version, and CPU governor state at runtime.
- Local output such as confidence intervals, outliers, and iteration counts should be inspected after each run but is not stored in git.
